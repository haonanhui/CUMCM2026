## 1. 目标与范围

交付一套三人可以分别在自己的电脑与 Agent 中使用、共同完成同一份竞赛作品的最小协作环境。核心方案为：
**“GitHub 私有仓库承载共享源码和持续协作，Release 承载精简部署包”**。

沿用现有流水线、数字冻结工具与论文模板，增加可移植入口、Git 共同历史、任务交接和独立结果目录。
中途正常的实现、检查、修复由执行 Agent 连续完成；涉及未知账号授权、不可恢复覆盖和最终竞赛提交时由真人决定。禁止新增中央服务器、跨机器 Agent 调度系统、阶段审批台或全局治理工程。

本规格中的新增路径和能力均为实施目标；现有工具能力须以源码与实际运行结果为准。

## 3. 三人职责与共同决策

默认职责可以按队员长项互换。每个任务卡指定唯一执行负责人；共同文件指定一个当班集成人。

| 成员槽位 | 默认主要职责 | 典型交付 |
|---|---|---|
| member-01 | 模型统筹与成果集成，建议由当前脚手架维护者承担 | 模型合同、任务分配、正式结果发布、集成快照 |
| member-02 | 数据、算法、数值实验 | 可重跑代码、参数、结果表图、误差与敏感性检查 |
| member-03 | 论文叙事与独立核验 | 提前建立论文结构、核验单位/约束/引用、整理论文与 AI 使用详情 |

三人共同理解题目、选择模型主线并复核重要结论。写作负责人从选题开始建立问题重述、符号、假设、方法章节骨架，待结果发布后填入版本绑定的图表与数字。任务可以围绕问题 Q1/Q2 或独立试验切分，各任务由负责人完成模型—代码—结果说明的局部闭环，避免反复口头转译。

开始并行前，用简短的 `docs/model-contract.md` 统一：赛题版本、各问依赖、数据列含义、单位、符号、约束、目标函数、评价指标及有效数据划分。存在依赖的任务使用明确版本输入；独立工作继续推进。每形成一个可复用成果即交接；建议每 2—3 小时进行一次简短集成，频率由真实进展调整。

## 4. 协作与版本模型

### 4.1 GitHub 私有仓库主干与分支协作

以 `https://github.com/haonanhui/CUMCM2026` 作为唯一的队内协作远端。保持仓库私有，保留现有协作者与权限配置。
`main` 分支保存已集成成果；任务分支使用 `work/<member-id>/<task-id>`；修复任务使用新分支。负责人通过 PR 或快速合并引入队友成果，并在合并后的集成版本上执行受影响检查。无需搭建外部审批系统。

设置严格的排除规则、检查待纳入清单，创建经过筛选的基线提交。禁止直接 `git add .` 将资料库、账户文件与本机上下文纳入历史。

代码、合同、依赖锁、实际调用的轻量 vendor、论文文本源、小型正式结果及数据清单入库。大体积原始资料、可再生试验中间文件和完整运行缓存通过队内受控文件传输分发，Git 中记录相对路径、文件大小和 SHA-256。数据文件勿用忽略整个 `data/` 的规则遮蔽正式结果。

活动工作副本、`.git`、虚拟环境与本地状态各由本机管理。三名成员分别在本地副本中运行 Agent。

### 4.2 GitHub Release 精简包与离线备选

GitHub Release 承载精简部署包（ZIP），供首次快速部署、离线备份与开箱即用。
发布包由经筛选核对的发布提交生成，附带 `bootstrap.json`、`START_HERE.md` 与 SHA-256 校验文件，排除 `.git`、本机凭证与大型无关资料。
此前规划的 Git bundle 离线路径降为可选备选手段；本轮无需实现独立的离线增量同步系统。队员直接通过私有 Git 仓库进行日常拉取与推送。

发布包前检查全部可达历史，确保从未包含排除资产或凭证。现有历史若包含敏感内容则暂停外发该候选包，报告具体情况。

## 5. 最小分发边界

### 5.1 核心内容

- 可移植 `AGENTS.md`/Agent 启动说明：项目目标、按需阅读入口、当前成员身份、协作合同与产出约定；不绑定某个厂商 harness。
- `code/pipeline/` 的实际工具、阶段 playbook 和测试；将正式 config 改为通用样例并保留训练样例。
- 经依赖核验的 Python 版本声明与 core 依赖锁，当前已识别 pypdf、python-docx、openpyxl、pandas、PyYAML；全部版本由干净环境测试确定。
- 阶段 playbook 实际引用的 vendor 文件、传递依赖及相应许可证/署名。保留原相对路径；运行中出现的按需引用也须纳入检查。必要时完整携带体积较小的被依赖 vendor 子树，优先保证可用性。
- 论文模板必需文本文件和构建说明。图形/优化等额外 Python 依赖按所用方法安装；LaTeX 能力单独记录，避免计算队员因缺少排版环境停工。字体文件与完整 TeX 发行版均排除分发。
- 简短协作规范、启动 JSON、任务/结果字段约定和合成测试数据。

### 5.2 排除内容

本机 project-control、OpenClaw、CodexScope、全局 Agent 配置、`.ai-bridge/` 本地会话状态、`AGENT_CONTEXT.md`、私人会话与日志、API key、token、`.env`、代理配置、虚拟环境、缓存、字体文件、历史优秀论文库、其他赛事整套数据、运行中间大文件。

本机 `PROJECT_ID.json` 及含主机路径的 `AGENT.md` 保留在原工作区，避免跨机同步；共享稳定 project_id 与可移植模板。接收端在自己的工作副本生成本地身份文件，根路径由解压/克隆位置推导。原有中央登记保持不变。现有身份文件须先比对；禁止覆盖不同项目的身份。

## 6. Agent 部署合同

设计输入为 `docs/TEAM_BOOTSTRAP_CONTRACT.json`；打包器生成实际包中的 `bootstrap.json`。二者区分设计状态与真实发布状态。

正式 bootstrap 至少记录：schema_version、project_id、release_id、source_commit、传输方式、包内文件清单与哈希、稳定入口、Python/依赖锁信息、成员配置、按能力划分的验证方法。包内路径统一相对路径，接收端拒绝绝对路径、`..` 越界和指向包外的符号链接。SHA-256 用于核对已知包的完整性，发送来源仍须由队友确认。

接收 Agent 按以下顺序连续执行：核对清单 → 克隆既定提交 → 识别本机系统与 Python → 创建项目局部虚拟环境 → 按已锁定依赖安装 → 生成本地配置 → 执行独立 smoke → 输出部署结果。Python 环境在目标机器重建；禁止复制维护者的 `.workbuddy` 解释器或覆盖队友的全局 AGENTS、代理、凭证。

core 与 paper 能力分别报告。缺少模型服务认证时由成员自行授权；打包程序和部署 Agent 均不得从维护者机器搬运账号配置。未知操作系统、Python 组合和论文构建能力记录为 UNVERIFIED。

重复部署时保留源代码、任务结果、现有配置与成员身份；发现版本/文件冲突就输出差异，避免覆盖。首次创建工作目录使用空目录；更新通过 Git 合并或已有版本明确支持的更新步骤进行。

## 7. 任务和结果接口

接口由简单文件与 Git 承载，不需要 JSON RPC、REST 服务或消息队列。

`team/tasks/<task_id>.json`：由当班集成人分配，包含 `task_id`、`owner`、`goal`、`base_commit`、`depends_on`、`input_manifest`、`write_paths`、`expected_outputs`、`acceptance`。依赖项指向确定的交付 ID/版本。任务状态由各自结果交接推导，避免多人争写同一任务卡。

任务运行输出：`data/contest/<contest>/<problem>/04_solve/runs/<member_id>-<task_id>-<run_id>/`。同一 run_id 的已交付文件保持不可变；重跑使用新 run_id。题目相关脚本接受输出目录参数，避免直接覆盖旧流水线默认公共目录。

每个结果包附 `result.json`，最低字段如下：

```json
{
  "schema_version": "1.0",
  "task_id": "q1-baseline",
  "member_id": "member-02",
  "run_id": "example-run-001",
  "status": "example_not_executed",
  "source": {"commit": null, "dirty": null, "patch_sha256": null},
  "inputs": [],
  "parameters": {"seed": 42},
  "metrics": {},
  "artifacts": [],
  "reproduce_argv": [],
  "validation": {"checks": [], "human_review": "pending"},
  "ai_usage_refs": []
}
```

示例保留空结果。真实交付填写输入文件哈希、模型合同版本、参数、随机性配置、命令参数数组、指标值与单位、图表路径与哈希、验证结果。相同种子无法保证所有算法/硬件逐位一致，数值容差须按指标指定。存在未提交代码时必须记录差异内容及其哈希，正式发布应能重建该源代码快照。

Agent 的自测结果与队员人工审查分别记录。真人未明确完成审查前，`human_review` 保持 pending；禁止代理补写真人通过。

## 8. 正式结果与论文汇合

沿用 `04_solve/frozen_numbers.json` 作为论文数值发布接口。当班集成人将任务结果转换为现有 `frozen_input` 格式，再调用原工具发布。其他任务写自己的运行目录。重复指标键遇到不同来源或不同数值时报告冲突，禁止静默覆盖。

每次发布记录来源 run_id、代码版本、输入哈希、验证状态和选定图表，形成确定发布版本。论文源使用模板占位符，构建副本负责数字注入，避免将唯一的源文件占位符永久替换。论文使用一份确定版本的数字与图表快照；新结果通过新发布版本整体更新。

共用 `main.tex`、参考文献文件、模型合同、正式数字表由指定当班负责人整合；各章节和任务代码可分文件并行修改。采用 DOCX 时由论文负责人维护主稿，其他人交付段落、表格与修改说明。

G1—G6 的检查结果继续提供诊断和提交依据。阻塞按实际依赖传播：数据未确认的计算暂停，独立的方法阅读、假设讨论、文稿骨架继续。去掉“每问固定两种方法”“固定参考文献数量”“新颖性字段即科学有效”等机械开工条件，以题意、证据和官方提交规则为准。

## 9. 学术规范与 AI 工具使用固定声明

为避免形式主义的逐次提问填报，团队统一执行固定合规声明政策（详见 `docs/AI_USAGE_STATEMENT.md`）：
- **定位与边界**：AI 工具严格限定用于文字语言润色、语法排版校对及文献背景检索等编辑性辅助支持。
- **独立研发**：所有物理机理分析、数学公式推导、核心求解算法架构与实验代码均由课题组成员独立研讨并实现，严禁利用 AI 工具直接生成核心算法或替代核心智力劳动。
- **免除过程填报**：无需在每个任务卡或结果包中动态记录交互过程，论文最终在参考文献前统一附注标准学术声明，既符合学术诚信要求，又杜绝无谓的流程负担。
- AI 规定：`https://www.mcm.edu.cn/html_cn/node/fef94648f2836ab6cc81586f4c38512b.html`
- 官网赛题发布与规则入口：`https://www.mcm.edu.cn/`
- Git bundle 官方手册：`https://git-scm.com/docs/git-bundle`
- Python venv 官方手册：`https://docs.python.org/3/library/venv.html`

## 10. 实施交付与验收

一次完成必要适配、部署包和实际演练，提交简短报告及证据路径：

1. Git 基线和任务分支已建立；本机治理文件与第三方资料排除边界清楚；原文件保留。实际远端尚未提供时离线模式可用。
2. 在含中文与空格的新目录从部署包建立独立副本；该环境不依赖维护者的中央治理目录、私有解释器和全局 harness 配置。
3. 核心依赖可重建，原有 smoke 在独立工作副本通过；paper 构建按实际能力单独实测和报告。
4. 以三份独立克隆模拟任务提交、两条分支合并、结果发布和论文引用，验证共同历史、路径可移植、结果无相互覆盖、版本一致。该演练标明同机模拟，队友真实设备部署情况独立登记。
5. 对缺失输入、错误哈希、越界路径、结果键冲突及重复安装保留文件执行最小针对性检查。失败记录具体能力与影响范围，不追加治理阶段。
6. 交付 `dist/cumcm-team-<version>.zip`、实际 bootstrap、文件清单/校验文件、发送给队友的 START_HERE、部署回执，以及简短实施报告。清单不得虚填 Git commit、依赖版本、大小、哈希或通过状态。

验收目标是队友 Agent 能在自己的工作区开始一个任务并交回可复用成果。主体可用后立即进入竞赛工作；周边可选能力按真实需要补齐。
